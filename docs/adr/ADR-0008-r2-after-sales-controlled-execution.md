# ADR-0008：R2 售后采用双确认、外部幂等与保守恢复

- 状态：已采纳
- 日期：2026-08-25

## 背景

R1 只读订单/保修 Mock 能证明客户归属与最小读取字段，但它不应自然演变为模型可调用的写接口。退货、补发和投诉即使在 Mock 环境中也会形成对客户可见的承诺；真实系统还可能涉及退款、库存、订单状态、通知、合规与补偿。数据库提交和外部系统提交之间不存在天然的单一原子事务，因此“请求重试”不能等价为“再次发送外部写入”。

当前合成 fixture 没有价格、退款规则、真实 OMS、真实 OIDC 或对外通知能力。将这些缺口伪装为已完成退款或已验证生产流程会造成错误验收。

## 候选方案

1. 让模型直接调用 OMS，并要求模型遵守确认与审批规则。
2. 让浏览器在客户确认后直接调用 Mock/OMS。
3. 在坐席审批 API 中同步调用 OMS，并在 HTTP 超时后直接重试。
4. 服务端持久化状态机；客户确认和坐席审批后才入队；受控 Worker 用稳定外部幂等键调用可查询最终状态的适配器。

## 决策

采用方案 4。

- R2 唯一允许的动作是 `return`、`replacement` 和 `complaint`。`refund`、`cancel` 与外部通知不是动作类型、没有 API 路由、没有浏览器按钮，也不能由模型参数绕过。
- 当前持久化草稿只能由同租户的 agent/supervisor 创建，并且必须绑定已有 Ticket。服务端从 Ticket 派生 tenant、customer 和内部订单绑定，使用确定性 Mock 政策再校验归属和资格。模型在后续若要参与，只能输出非执行性的结构化建议；坐席仍必须以自己的权限提交草稿。当前不会把模型输出直接持久化为售后工作流。
- 新草稿在同一事务中记录 `draft_created`、`policy_checked` 和客户确认请求事件，最终稳定在 `awaiting_customer_confirmation`。客户确认要求当前已验证客户身份；坐席审批要求 agent/supervisor 角色。两者都满足后才进入 `queued`。坐席对动作类型作实质编辑会清除先前确认，并受控地回到客户重新确认，而不是沿用旧同意。
- 每个 HTTP 写操作都要求 `Idempotency-Key`。记录按 tenant、principal、操作和 key digest 唯一化；同 key 同请求返回首次响应，同 key 改变请求返回 `409`。这保护 API 重放，但不代替业务/外部幂等。
- Worker 只消费 `queued` 工作流。外部键由 `workflow_id` 确定性派生，数据库只保留其 digest；Mock OMS 在独立 session 的 `mock_oms_operations` 账本中以 tenant + 外部 key digest 唯一化。即使 Worker 在 OMS 已提交后崩溃，恢复也只能 `lookup` 同一外部键，不能再次 `execute`。
- Worker 在外部写之前重新验证：工作流状态、当前客户验证等级/归属、客户确认人、审批人角色和租户、Ticket-订单绑定、当前确定性政策快照以及外部幂等键 digest。任一失败都以明确失败码结束，不调用 OMS。
- 超时或传输不确定时，工作流保持 `executing` 且标记 `pending_reconciliation`；Worker 仅查询最终状态。查询为 `completed`、`failed` 或 `compensation_required` 时才落到相应终态；查无该操作时明确失败。不会静默重新写入外部系统。
- 工作流事件使用每个 workflow 单调递增且唯一的 `sequence`，不以同一事务内可能相同的时间戳排序。操作前后都写入最小审计摘要、事件、状态、回执投影及补偿原因码。

## 后果

正面结果：

- 客户无法在未验证或非本人资源上确认；坐席不能在未确认的草稿上排队；浏览器与模型都不能执行副作用。
- 重复 HTTP 提交、重复 Worker 消费和 Worker 崩溃后恢复不应产生重复的 Mock OMS 请求。
- 客户可以看到等待核对、失败和补偿状态，但不会得到原始外部错误、外部幂等键、内部客户 ID 或租户 ID。

限制与生产门禁：

- 当前规则只是合成 fixture：退货要求 `delivered`，补发要求 `delivered + active warranty`，投诉要求已验证归属；它不代表真实售后、价格、税费、退款、库存、物流或法律政策。
- 当前 Worker 是数据库轮询和租约恢复，不是生产 durable queue/Outbox、调度、死信队列、告警、值班、全局限流或多区域可用性方案。
- Mock OMS 的独立 session 只能演练协议语义，不能证明真实供应商的鉴权、网络分区、Webhook、最终一致性、速率限制、SLA、数据保留或补偿能力。真实适配器必须承诺外部幂等写和按同一 key 查询最终态。
- Demo Header、`demo_verified`、本地合成数据和有限的审计字段投影不能进入生产。真实接入还需要可信 IdP assurance、数据分类/DLP、加密与保留策略、审计导出、运营审批职责、业务负责人验收和故障演练。

## 验证

- API 测试覆盖确定性资格、禁止动作类型、客户归属、跨租户隐藏、角色限制、草稿编辑后重新确认、API 幂等冲突、审计最小化和不调用 LLM Gateway。
- Worker 测试覆盖审批前无外部写、Mock OMS 重放去重、超时后仅 lookup、崩溃后查无操作失败、补偿终态与不重试。
- Playwright 覆盖坐席创建草稿、客户查看摘要并确认、坐席审批入队，以及 UI 明确显示尚未产生外部动作。
