# ADR-0009：主管 QA 以最小证据、受控停用和回归映射闭环

- 状态：已采纳
- 日期：2026-08-25

## 背景

步骤 32–36 已有客户“有帮助/没有帮助”信号、人工升级上下文、审计事件和 R0/R2
保护，但这些能力不能回答一个主管 QA 问题：某个错误答案为什么发生、谁负责修复、
修复属于知识还是规则、是否已进入可重复执行的回归、以及验证结果是什么。

客户反馈不是事实判定，也不能自动改写知识、ACL 或路由。直接把完整客户会话、模型
隐式推理或 provider 原始 trace 复制到 QA 表，又会制造未经治理的影子数据集。

## 候选方案

1. 将客户的负面反馈自动视为错误并自动修改知识或路由。
2. 只在 Prompt、工单备注或人工文档里记录问题，不持久化根因和回归关联。
3. 保存完整会话、模型 Prompt 和原始供应商 trace，便于日后人工检索。
4. 仅允许主管在租户范围内抽样；保存可复核的脱敏视图和不可逆证据摘要；让每个
   问题显式绑定根因、修复、负责人和已存在的评测 Case，再通过状态机记录验证结果。

## 决策

采用方案 4。

- `/v1/admin/qa/*` 的所有端点都由服务端要求 `supervisor` 角色，并按当前租户过滤。
  跨租户会话、负责人和问题返回隐藏式 `404`；客户、坐席和知识运营角色不能读取或
  修改 QA 闭环。
- 主管抽样只能看到已完成助手答复的会话。显示模型使用的最终结果、路由、客户可见
  引用、最小工具摘要和客户反馈计数；所有会话文本及主管自由文本先做直接标识符
  脱敏。问题记录中的 `source_snapshot` 只保存消息 ID、角色、响应类型、内容哈希、
  路由、引用版本/摘录哈希、工具摘要和反馈计数，不复制原始会话或隐藏 Prompt/Trace。
  幂等记录只保存 `issue_id`，重放时从受控问题重新投影，避免再次复制样本。
- 每个问题必须有分类、严重程度、根因、负责人、修复类型、修复说明和回归目录条目。
  分类覆盖事实、引用、过期政策、路由、升级、权限/隐私、工具参数、UI 和坐席误用。
  生命周期为 `open -> in_remediation -> verification_pending -> verified -> closed`，
  并只允许受控回退。标记 `verified` 必须同时有 `passed` 回归状态和非空运行证据引用。
- 高或严重问题可以在同一事务中关闭当前租户 R0 功能开关，并写入最小审计摘要；QA
  接口永远不能重新开启 R0。既有灰度名单不被删除，重新开启需要独立的主管操作、
  风险复核和发布批准。
- `data/evals/qa/regression-catalog.json` 将 QA 问题映射到 triage/RAG 的公开合成 Case。
  API 在创建时验证分类、修复类型和 Case ID 一致，加载目录时验证目标 Case 确实被
  既有评测器读取。因此“已绑定回归”至少有可执行含义，不是自由文本宣称。
- 首批闭环资产同时包含知识修复和规则修复：RAG 语料将 45 天的历史退款政策标为
  expired、发布当前 30 天 v2；补发/补寄/换货/换新在 R0 门禁、Fake Gateway 和模型
  输出强制策略中都进入 R2 人工审核，防止仅修改某一层而被其他入口绕过。

## 后果

正面结果：

- 主管能从坏例追溯到受控版本、路由与证据摘要，分配根因和负责人，并看到修复是否
  已被合成评测执行和通过。
- 暂停自动化是可审计、租户局部且只能关闭的安全动作；浏览器和模型不能借 QA 接口
  重新开启功能。
- 回归目录把数据/规则修复从“改了说明”提升为可运行的开发资产。

限制与生产门禁：

- 这是 Local/CI 合成 QA 基线，不是不可篡改的生产质量系统、法务事件系统或真实
  客户质检平台。当前没有生产 Retention/Legal Hold、加密密钥隔离、审计导出、SIEM、
  真实指标采样、外部工单同步、分级值班或生产 CI 签字记录。
- 脱敏是最小直接标识符规则，不替代数据分类、DLP 或“可以复制真实客户内容”的许可。
- 目录中的 Case 是公开仓库里的合成回归，而不是独立盲测、真实模型证明或真实政策
  签字。通过它不构成生产模型或企业生产 `GO`。

## 验证

- API 测试覆盖角色/租户边界、样本脱敏、证据不复制、负责人边界、R0 仅关闭、幂等、
  状态机、验证证据要求、审计和回归目录完整性。
- 分诊评测加入补发/换货 R2 回归；RAG 评测加入当前退款政策 v2 回归，并验证历史
  45 天结论不进入答案。
- Playwright 覆盖主管从真实合成会话选择样本、登记问题、绑定规则回归并完成
  `in_remediation -> verification_pending -> verified` 的浏览器闭环。
