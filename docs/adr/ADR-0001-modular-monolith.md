# ADR-0001：P0 采用模块化单体

- 状态：已采纳
- 日期：2026-08-12

## 背景

P0 需要快速验证工单、权限、状态机和审计。当前没有独立扩缩容、独立发布或故障隔离证据，过早拆分微服务会增加网络、部署、数据一致性和排错成本。

## 候选方案

1. 无明确边界的单体。
2. 有清晰模块边界的模块化单体。
3. 按业务域拆分微服务。

## 决策

采用模块化单体。后端业务先放在一个可部署 API 中，按 Identity、Ticket、Audit 等模块划分边界。

Next.js 前端和 Worker 可以是独立运行进程，但不把每个业务模块拆成网络服务。

## 后果

正面结果：

- 本地开发、测试和部署更简单。
- 跨模块事务更容易保持一致。
- 初学阶段更容易定位问题。

成本与限制：

- 必须主动维护模块边界，避免演变为“大泥球”。
- 单体内的错误可能影响整个 API。
- 未来拆分需要额外迁移工作。

## 验证

- 业务模块有明确目录和职责。
- 模块通过公开接口协作，不随意访问其他模块内部实现。
- P0 不引入按业务域拆分的网络服务。
- 只有出现独立扩缩容、发布或隔离证据时才重新评估微服务。
