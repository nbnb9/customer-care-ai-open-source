# ADR-0004：客户会话采用持久事件序列与受控 SSE

- 状态：已采纳
- 日期：2026-08-24

## 背景

客户会话需要在网络中断、浏览器刷新和重复提交后仍保持消息顺序，且不能把模型文本流误展示为订单、退款或人工服务已经完成。当前 Demo 身份通过请求头传递；原生浏览器 `EventSource` 不能安全附加该头。

## 候选方案

1. 只在浏览器内保存聊天记录，发生断线后从模型重新生成。
2. 使用内存 Pub/Sub 推送流式 token，不持久化事件。
3. 在数据库中持久化会话、消息和严格递增事件序列，以 SSE 补偿恢复。

## 决策

采用方案 3。

- 每个会话写入都锁定会话行后分配唯一 `sequence`，并持久化事件、`event_id`、`request_id` 和服务端构造的 payload。
- SSE 的 `id` 采用 sequence。客户端通过 `after_sequence` 或 `Last-Event-ID` 请求严格后缀，并忽略已确认的重复事件。
- `answer.delta` 只携带文本增量；引用、允许操作和最终文本只能由 `answer.completed` 产生。客户人工升级通过单独的 `handoff.created` / `workflow.updated` 事件确认。
- 当前 Demo 前端用带身份头的 `fetch` 读取 `text/event-stream`，不把身份放进 URL。真实 OIDC Cookie/Token 方案可在后续认证阶段重新评估。
- 202 后的本地回复续作使用 FastAPI `BackgroundTasks`，但它只证明 Local/CI 语义；不能被解释为生产级可靠队列。
- 步骤 32 的原始范围不打开 R0 FAQ 或业务工具；该历史基线中的正常消息仅返回固定的非政策确认。步骤 33 对受控 R0 的后续决策见 [`ADR-0005`](ADR-0005-r0-public-faq-feature-flag.md)，仍保留高风险确定性人工升级。

## 后果

正面结果：

- 断线恢复不依赖模型重新生成，也不会改变先前事件顺序。
- 重复提交能由幂等记录收敛，事件和人工升级可审计。
- 前端只渲染服务端授权的事件，不持有租户/客户真相或业务完成状态。

成本与限制：

- 原始会话内容当前仅限合成数据，尚未具备生产保留、删除、加密和脱敏策略。
- 数据库轮询 SSE 适合当前单体基线，不等同于高并发消息总线。
- `BackgroundTasks` 进程崩溃后没有 durable retry；生产需要 Outbox、队列、worker 领用和恢复演练。
- 客户级数据库限流是起步防护，不是跨区域全局限流。

## 验证

- 跨客户、跨租户和非客户角色无法订阅其他会话。
- 同一会话的事件序列严格递增；按 cursor 恢复只得到严格后缀。
- `answer.delta` 不含引用或允许动作，`answer.completed` 才含最终响应字段。
- 并发相同 `Idempotency-Key` 不创建重复消息、回复或事件。
- 生成失败产生可操作 `error` 事件，浏览器不会永久保持 loading。
