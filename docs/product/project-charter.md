# CustomerCare AI 项目章程：P0 无 AI 服务台

- 状态：已采纳
- 日期：2026-08-12
- 当前里程碑：P0
- 数据边界：只使用完全合成的数据

## 目标

先建立一个确定性、可测试、可审计的无 AI 客服基线，再判断后续 AI 是否真正改善处理效率和质量。

## 目标用户

| 用户 | P0 中的任务 |
|---|---|
| 客户 | 创建工单、查看自己的工单和回复 |
| 一线坐席 | 查看队列、领取工单、回复、变更状态 |
| 主管 | 查看队列、重新分配、发现错误路由 |
| 知识运营 | 属于目标用户，但 P0 暂不实现知识库管理 |

## P0 范围

- 合成客户创建并查看自己的工单。
- 合成坐席领取、回复和变更工单状态。
- 合成主管查看队列和重新分配工单。
- 记录操作者、时间、状态变化和必要审计事件。
- 使用合成身份验证租户与角色边界。

## P0 不做什么

- 不连接真实 SSO。
- 不连接真实 CRM、OMS 或物流系统。
- 不使用模型、RAG、Embedding 或 Agent。
- 不执行退款、取消订单或真实外部写操作。
- 不自动向真实客户发送消息。
- 不导入真实客户、订单、工单或聊天数据。

不接真实 SSO 不等于不测试权限；P0 仍需用合成身份验证租户隔离和角色权限。

## 无 AI 基线

| 指标 | P0 定义 | 证据 |
|---|---|---|
| 人工分诊时间 | 工单进入未分配队列到首次有效分配的时间 | 工单事件时间戳 |
| 转交次数 | 首次分配后负责人或队列变更次数 | 分配事件 |
| 错误路由 | 被主管以错误队列原因重新分配的工单数 | 原因码和审计事件 |
| 重复提交 | 被幂等规则拒绝或关联的重复请求数 | 幂等键和关联记录 |
| 非法状态跳转 | 被状态机拒绝的状态变更数 | 错误码和审计日志 |

当前阶段先定义口径并建立基线，不虚构目标百分比。阈值需要根据后续测量结果和错误成本决定。

## 成功标准

- 一个合成客户可以创建工单并只能查看自己的工单。
- 一个合成坐席可以领取、回复并按允许路径变更状态。
- 一个合成主管可以查看队列并重新分配工单。
- 每次关键变化都记录操作者、时间、前后状态。
- 非法状态跳转被明确拒绝。
- 重复请求不会创建重复副作用。
- 系统只在数据真正持久化后报告成功。
- 全部流程不依赖模型和真实企业数据。

## 主要风险与控制

| 风险 | 控制 | 后续验证 |
|---|---|---|
| 租户越权 | 服务端租户与角色检查 | 跨租户访问测试必须失败 |
| 状态乱跳 | 确定性状态机 | 非法转换测试 |
| 重复提交 | Idempotency-Key | 重放测试 |
| 假成功 | 成功响应必须对应已持久化状态 | 失败注入与回读验证 |
| 真实数据混入 | 仅允许合成 Fixture | 仓库审查与安全检查 |

## 为什么 P0 不需要 AI

P0 要验证的是工单、权限、状态、幂等和审计这些确定性基础。如果这些基础还不可靠，加入模型只会增加随机性、成本和排错变量，也无法判断 AI 是否真的带来改善。因此先建立无 AI 基线，再用同一套指标比较后续 AI 阶段。
