# 真实坐席任务完成率与处理效率验收

- 阶段：步骤 41.5 / PZ-4
- 状态：验收协议草案；首轮测试前由产品、运营、安全共同冻结
- 目的：证明产品帮助真实坐席更快、更正确地完成售后任务，而不是证明页面“看起来更好”

## 测量原则

任务成功率、时间和满意度分别对应可用性的有效性、效率和主观体验。三者不能互相替代：

- 点击更少但执行了错误售后，不算成功。
- 任务成功但依赖主持人提示，不算无协助成功。
- AI 接受率高可能来自盲从，不能直接当作质量或效率指标。
- 网络等待、客户等待和坐席主动操作时间分别记录，不能把系统延迟隐藏在“平均处理时长”中。
- 研究样本只支持本阶段门禁，不自动证明所有行业、语言和组织都能获得同样结果。

## 参与者

正式门禁至少包括：

- 12 名非项目成员的一线售后坐席；过去 12 个月内实际处理过消费电子/智能硬件的订单、保修、
  退换或投诉。
- 其中至少 4 名近期入职坐席、4 名有一年以上经验坐席；其余按试点企业实际构成招募。
- 至少来自 2 个团队或品牌，避免把单一组织习惯误当作通用产品需求。
- 另招募至少 2 名主管/QA 执行队列和质量任务，但主管结果单独报告。

参与者使用合成身份、合成客户和 Shopify Dev Store 测试订单。研究前取得记录同意；记录中使用
参与者编号，不能收集真实客户消息、订单、地址、电话、账号或生产屏幕。

## 对照方法

采用同一参与者内的基线/原型对照，并对工具顺序进行平衡：

1. 在当前工具或当前 Demo 中执行冻结任务，获得基线。
2. 接受不超过统一脚本范围的产品介绍。
3. 在产品化原型/实现中执行等价但不同数据的任务。
4. 一半参与者先做基线，一半先做新方案，降低学习顺序偏差。
5. 所有任务在测试开始前定义正确答案、允许路径、严重错误和计时边界。

若试点企业无法提供现有工具沙箱，可使用“当前项目界面 + Shopify Admin”作为工程基线，但报告
必须注明它不能代表该企业真实生产效率。

## 六个核心坐席任务

| ID | 任务 | 成功条件 | 严重错误 |
|---|---|---|---|
| A1 | 从队列找到并领取最应优先处理的工作 | 选择正确租户/队列工作项，说明 SLA/风险排序理由并成功领取 | 打开跨租户内容、忽略安全升级、错误转交 |
| A2 | 理解客户问题并核对订单/保修 | 找到正确客户、订单、履约、设备和保修结论；不暴露无关敏感字段 | 使用其他客户订单、把未验证身份当作已验证 |
| A3 | 基于知识证据形成客户回复 | 找到当前有效来源，解释关键结论，编辑并发送客户可见回复 | 引用撤回/过期/越权来源，虚构结论，发送内部备注 |
| A4 | 创建并推进 RMA/退货草稿 | 选择正确对象/原因，完成政策检查、客户确认请求和人员审批前步骤 | 未确认/未审批即外部执行，误把草稿写成已完成 |
| A5 | 识别安全/严重投诉并升级 | 进入正确安全/投诉队列，保留必要上下文，隐藏不适用自动动作 | 降低风险、关闭为普通 FAQ、自动补发/退款 |
| A6 | 处理外部结果不确定 | 判断是否可能已产生副作用，使用同一外部键回查或转调查，不盲目重发 | 重复创建 return、伪报成功、丢失审计关联 |

主管补充任务：识别即将超 SLA 队列、重新分配、从坏例创建 QA 修复、暂停有风险的 R0、从业务
异常下钻到技术证据。主管任务不计入一线坐席总体完成率。

## 计时边界

每个任务记录：

- `elapsed_time`：主持人读完任务到参与者声明完成或终止。
- `active_handle_time`：排除明确的系统等待、测试客户确认等待和主持人处理测试故障。
- `system_wait_time`：接口、页面、模型和外部沙箱等待。
- `context_switches`：离开当前工作区进入 Shopify Admin、其他工具、文档或手工记录的次数。
- `backtracks`：进入错误区域后返回并改走另一条路径的次数。

计时不以“首次点击提交”结束；必须回读正确最终状态或明确进入安全的 pending/investigation 状态。

## 成功编码

| 结果 | 定义 | 计入无协助成功率 |
|---|---|---|
| 成功 | 在时限内达到全部正确状态，无主持人提示、无严重错误 | 是 |
| 成功但低效 | 正确完成，但超过预设时限或明显多次回退 | 是，单独标记 |
| 提示后成功 | 主持人给出方向、功能位置或业务规则提示后完成 | 否 |
| 失败 | 未完成、错误结束或触发严重错误 | 否 |
| 测试故障 | 沙箱/设备故障使任务无法继续 | 排除，但必须保留故障证据并补测 |

时限根据 PZ-0 基线分布在正式测试前冻结，不在本文预设同一个分钟数。提前设置统一分钟数会把任务
复杂度差异误当作产品差异。

## GO / NO-GO 阈值

以下数字是项目发布门禁，不是行业平均值；在第一位正式参与者开始前冻结。

### 有效性

- A1–A6 总体无协助完成率 `>= 90%`。
- 任一单项任务无协助完成率不得低于 `80%`。
- A2、A4、A5、A6 的归属、审批、安全和外部副作用严重错误必须为 `0`。
- 跨租户暴露、错误客户订单、非预期真实/沙箱外部写入、重复外部 return 必须为 `0`。

### 效率

- A2（订单/保修）、A3（证据回复）、A4（售后草稿）三项的中位 `active_handle_time` 相对冻结
  基线至少降低 `20%`。
- 三项的 P75 `active_handle_time` 均不得高于基线 P75；避免只优化熟练用户而伤害慢用户。
- 三项合并的中位 `context_switches` 相对基线至少降低 `50%`。
- `system_wait_time` 单独报告；不能通过剔除失败/超时样本制造效率改善。

### 主观体验与信心（辅助门禁）

- 每项任务完成后的 7 分单题易用度（SEQ 风格）中位数至少 `5`。
- 对“我能分辨建议、草稿和已执行状态”“我知道下一责任人”“我能验证 AI 来源”三项，
  7 分量表中位数至少 `6`。
- 任何参与者把草稿误解为已执行，即使任务最终完成，也产生至少一个高优先级可用性问题。

## 结果报告

报告必须包含：

- 冻结的任务脚本、正确答案、计时边界和阈值版本。
- 参与者构成、经验、团队来源和招募偏差，不记录真实姓名。
- 每个任务的成功/提示/失败、时间分布、上下文切换、严重错误和观察摘要。
- 基线与新方案的中位数、P75 和原始匿名化逐任务记录；不只报告平均数。
- 系统故障、缺失样本、主持人偏差和学习效应。
- 所有未关闭问题的严重度、负责人、修复方式和回归任务。

研究原始数据保存在受控位置，仓库只提交去标识汇总与合成复现。视频、音频和带人脸/声音的材料
不得提交 Git。

## 阻断规则

以下任一情况直接判定 NO-GO，不用总体分数抵消：

- 任何跨租户或错误客户数据暴露。
- 任何没有正确确认/审批的外部写入。
- 任何结果不确定时的盲目重发或虚假成功。
- 任何安全事件被产品默认路径降级为普通处理。
- 正式任务开始后修改正确答案、排除不利样本或降低阈值。
- 参与者不是目标领域真实坐席，却在报告中写成“真实坐席验收”。
