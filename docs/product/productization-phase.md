# 步骤 41.5：产品化重构阶段

- 状态：已批准，执行中
- 插入日期：2026-08-30
- 前置基线：步骤 1–41 的 Local/CI 合成能力
- 后续门禁：本阶段未通过前，原步骤 42（Staging/CD）保持暂停
- 数据边界：用户研究可以观察真实坐席，但产品测试只使用合成数据和供应商开发沙箱
- 当前证据：[产品化 GO 证据登记表](productization-go-register.md)

## 决策摘要

当前仓库证明了租户隔离、证据约束、人工接管、售后确认/审批、幂等、审计和本地可观测性，
但 Web 仍是工程验证界面。继续把它包装成通用工单系统会同时面对 Zendesk、Intercom、
Freshdesk；若直接收窄为 Shopify AI 客服，又会正面面对 Gorgias 的订单侧边栏、退货/取消/
补发动作和多渠道 AI。

因此本阶段采用以下**待验证产品假设**，而不是把它写成已经得到市场证明的事实：

> 为已经使用工单系统和电商/OMS 的高客单消费电子与智能硬件品牌，提供一个审批优先、
> 可审计、支持保修/RMA 的 AI 售后协同层；减少坐席跨系统查找与重复录入，同时避免模型
> 或一线坐席未经授权执行高成本售后动作。

首个真实系统选择 Shopify Dev Store。它只用于验证真实订单/退货契约，不代表目标客户必须
使用 Shopify，也不构成生产供应商选择。产品以适配器接入现有工单和 OMS，不以替换完整
全渠道客服平台为首期目标。

|---|---|---|

| 改造前基线（已修复） | 前端曾没有仓库内设计系统、用户研究协议或自动可访问性门禁 | 已建立 token、组件、内容规范、研究协议，以及 WCAG/键盘/回流 E2E |

| 待验证 | 消费电子/智能硬件比通用电商更需要保修、序列号、维修和安全事件能力 | 至少三个目标企业的情境访谈 |

## 目标细分行业与购买者

### 首选细分行业

- 跨境或多区域销售的消费电子、智能硬件、家电配件品牌。
- 已有工单/聊天工具以及 Shopify 或其他 OMS，不愿整体迁移客服平台。
- 售后包含订单查询、保修资格、RMA、退货、补发、投诉或安全事件升级。
- 错误补发、错误退货、越权退款或跨租户数据暴露具有可见成本。

### 明确不做

- 首期不做通用 CRM、呼叫中心、WFM 或全渠道平台替代品。
- 不用“一个 AI 自动解决所有客服问题”作为销售承诺。
- 不在本阶段连接真实支付，不自动退款或取消真实订单。
- 不把金融、医疗等强监管行业作为未经领域验证的首发市场。

### 购买与使用角色

| 角色 | 购买任务 | 需要看到的证据 |
|---|---|---|
| 经济购买者：售后/CX 负责人 | 降低每单处理成本和错误售后成本，不牺牲体验 | 基线对照、处理时长、错误率、试点 ROI 假设 |
| 内部推动者：客服运营/AI 转型负责人 | 将政策、知识、审批和现有系统组成可运营流程 | 配置能力、灰度、QA、回滚、版本与成本 |
| 一线用户：售后坐席 | 少切系统、快速理解上下文、完成可追溯动作 | 任务完成率、时间、上下文切换次数 |
| 管理用户：主管/QA/知识运营 | 看队列风险、抽检 AI、修复知识与流程 | 可下钻的质量与风险视图，而不是原始 Trace 堆叠 |
| 阻断者：IT/安全/法务 | 控制身份、数据、权限、密钥、外部动作和保留 | 最小权限、审计、数据流、故障/撤销演练 |

## 竞争基线与差异化约束

以下仅使用厂商官方能力页说明买家会比较什么；它们是供应商陈述，不是独立排名或效果证明。

| 产品 | 官方展示的能力基线 | 对本项目的含义 |
|---|---|---|
| Zendesk | 跨渠道统一坐席工作区、客户中心视图、全渠道路由 | 不能用一个两栏工单页宣称“统一工作台” |
| Intercom | 统一 Inbox、工作量、SLA、Workflow、实时和自定义报表 | 不应首期复制完整帮助台；要嵌入或协同 |
| Freshdesk | 邮件/聊天/语音、跨渠道上下文、AI/人工交接、规则和指标 | 单一 Web 表单不构成全渠道竞争力 |
| Gorgias | Shopify 订单上下文、退货/取消/退款/补发动作、AI 和品牌知识 | “电商 AI + Shopify”本身没有差异化 |

候选差异化必须同时满足：

1. 售后动作由服务端政策、客户确认和人员审批共同约束。
2. 保修/RMA、安全事件和高成本例外是核心任务，而不是通用 FAQ 的附属项。
3. 每个建议、证据、批准、外部调用和最终回执可复核。
4. 能作为现有帮助台/OMS 的协同层接入，而不是强迫客户迁移全部渠道。
5. 价值用真实坐席任务与错误成本测量，不用模型调用次数代替业务结果。

## 工作流与阶段门禁

### PZ-0：问题与购买验证

招募、访谈、反证和综合规则见
[`product-discovery-research-plan.md`](product-discovery-research-plan.md)。

交付物：

- 至少 3 家目标企业的当前售后旅程图。
- 经济购买者/推动者访谈不少于 5 人；真实一线坐席情境观察不少于 8 人；主管/QA 和
  IT/安全各不少于 2 人。人数是本项目的最低证据门槛，不代表统计推断。
- 记录高频任务、当前工具、等待时间、返工、错误动作及可接受部署方式。
- 明确一个可签署沙箱试点意向的目标企业；没有试点意向则重新定位，不进入 UI 重写。

门禁：至少 3 家企业确认同一个高价值问题，且问题不能由现有帮助台的简单配置直接解决。

### PZ-1：信息架构与关键原型

交付物：

- 客户嵌入式入口、坐席协同台、主管运营台、管理配置台四个角色外壳。
- 订单查询、带证据回答、RMA/退货草稿、客户确认、坐席审批、安全升级六条关键任务流。
- 可点击原型以及明确的成功/失败状态；Demo 身份和步骤编号不出现在市场界面。
- 任务定义和观察脚本在测试前冻结，避免按测试结果修改成功口径。

门禁：第一轮真实坐席测试不得出现身份混淆、找不到主任务或误把草稿当成已执行。

### PZ-2：设计系统和前端壳层

交付物：

- 语义颜色、字体、间距、密度、焦点、状态和动作风险 token。
- App Shell、队列项、会话、客户/订单上下文、证据卡、政策卡、审批步骤、时间线、
  空/错/加载状态组件。
- WCAG 2.2 AA 自动检查、键盘路径、200% 缩放和窄屏回流验收。
- 旧页面迁移清单；不允许继续新增散落的硬编码颜色和无状态定义组件。

门禁：核心原型通过视觉、键盘、对比度和状态覆盖检查后，才能迁移真实 API 页面。

### PZ-3：真实 Shopify OMS 沙箱

交付物：

- Shopify Dev Store、生成测试数据、Bogus payment gateway 和受控应用凭据。
- 第一阶段只读订单/履约/退货状态适配器；Mock 仍是 CI 默认，真实沙箱只在专用 job 启用。
- 第二阶段仅在沙箱尝试 `returnCreate`；退款、取消和支付 scope 不申请。
- 版本化外部命令、最小权限、HMAC webhook、重复 delivery 去重、限流和故障回查测试。
- 凭据只存在本机/CI secret store；日志、Trace、截图和研究记录不得包含 token 或客户字段。

门禁：真实沙箱读契约、失败降级和租户/客户归属全部通过；任何不确定写入无法可靠回查时，
写路径保持关闭，不能为了阶段进度降低幂等要求。

### PZ-4：真实坐席任务验收

交付物与阈值见
[`agent-usability-acceptance.md`](agent-usability-acceptance.md)。核心门禁为：

- 至少 12 名非项目成员、近期做过目标领域售后的真实坐席参与对照测试。
- 六个核心任务总体无协助完成率至少 90%，单任务不得低于 80%。
- 高风险归属/审批/安全任务必须 100% 正确，严重错误和非预期外部写入为 0。
- 三个高频任务的中位主动处理时长相对冻结基线至少降低 20%，P75 不得恶化。
- 结果必须附原始匿名化观察记录、任务定义、样本构成和置信限制；不把小样本外推为市场证明。

这些数值是本项目的产品发布门禁，不是行业平均值。PZ-0 若显示错误成本或基线不同，允许在
测试开始前由产品、运营和安全负责人共同调整；测试开始后不得追改阈值。

## 步骤 42 的解锁条件

只有同时满足以下条件才恢复原步骤 42：

1. PZ-0 的问题/购买假设得到目标企业证据，或明确记录定位调整。
2. PZ-1/PZ-2 的关键原型、设计系统和核心前端壳层验收通过。
3. Shopify 真实只读沙箱通过；写路径若未证明可回查，明确保持关闭。
4. PZ-4 真实坐席任务门禁通过，且没有未关闭的严重可用性或安全问题。
5. 产品负责人、售后运营负责人和安全负责人分别授权进入 Staging；工程完成不能代替三方授权。

截至 2026-08-31，PZ-1/PZ-2 的仓库工程基线已完成；PZ-3 的只读实现和离线测试已完成，但真实
Dev Store 运行尚无凭据/结果；PZ-0、PZ-4 和三方授权没有真实证据。不能把自动化测试数量替代
外部研究和授权，当前解锁结论仍为 **NO-GO**。
